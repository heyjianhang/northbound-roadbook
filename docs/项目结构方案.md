## 总体选择

一个仓库、一个 Web 应用、一套轻量 Node 服务。沿用已有 React、TypeScript、Vinext / Vite、Tailwind 和 shadcn / Base UI；保留依赖锁文件。页面入口保持简短，实际界面按功能组织，地点操作、路线规划、存储和 PWA 缓存分别集中。

首版使用本机数据与 JSON 导入导出；Node 服务负责静态页面和高德 JS API 代理。共享路书或账号同步若后续需要，再单独定义服务端接口与冲突处理。

## 层次与职责

| 层次 | 负责什么 | 具体约束 |
| --- | --- | --- |
| app | URL、布局、加载业务页面 | 不在 page.tsx 内集中写算路、存储与数据迁移 |
| features/trip | 路书事实和用户操作 | 所有地点平级；路书页、地图页读取同一份状态 |
| features/roadbook、places、map | 用户界面 | 编辑表单先保留草稿，保存后再提交地点操作 |
| features/routing | 根据地点变化重新规划 | 挂在共享 Provider 中；即使地图页没打开，路书页仍可触发算路 |
| lib/amap | SDK 与查询适配 | 保留原查询结果里的里程；不从简化轨迹计算道路里程 |
| lib/storage | 本机保存、迁移、备份 | 事务成功才显示已保存；读取失败不能用初始数据覆盖旧记录 |
| pwa + public/sw.js | 应用资源缓存、安装、更新 | 与用户路书数据分开，更新网页不删除个人路书 |
| scripts | 构建和服务运行 | 继续让 JS 安全密钥留在 Node 代理端 |

状态管理首版可使用 React Context / useReducer，围绕一个 TripStore 组织；不因为拆页面再为每页新建一份行程。地图 SDK 实例由画布组件管理，路书本体和查询状态放在共享层。

## 核心数据

建议把新路书格式升为 v3，核心关系是：

```text
Trip
 +-- Day 2026-10-01
 |    +-- Stop 01
 |    +-- Stop 02
 +-- Day 2026-10-02
      +-- Stop 03
      +-- Stop 04
```

Stop 表示“某天的一次停靠”，包含自己的 ID、名称、坐标、可选高德 POI ID、停留时间、备注和攻略。没有 priority、required、anchor 或 enabled 等等级 / 锁定字段。数组顺序就是当天顺序；相同地点在不同日期或同一天再次停留时，使用不同 Stop ID，编辑一项不会意外改动其他停靠。

路线记录与用户地点分开保存，以两端坐标、方向、路线策略匹配；当前路段另关联两端 Stop ID。0 个或 1 个地点可正常保存；2 个及以上且坐标有效才算路。缺少任一路段时，不把已查部分冒充完整的全天总里程。

迁移旧 v1/v2 时，先备份，再把原先启用的 visits 按顺序转成平级 Stop，复制其对应地点资料；旧版关闭或未安排的地点资料保留在导出数据的未安排资料区，不自动塞回当天行程。原攻略、用户备注和可验证的基础路线记录保留。新字段具体定义在实施时写入 DATA_FORMAT.md，旧输入只经 migrations.ts 转换。

## 删除地点时的数据流

```text
路书页或地图页：删除 B
          |
          v
commands：A -> B -> C 变为 A -> C
          |
          +--> TripStore 通知所有页面，显示撤销
          +--> repository 保存新的地点列表
          +--> selectors 识别当前有效路段
                         |
                         v
                 route coordinator
                  /              \
              有网                离线
               |                   |
          查 A -> C           标记待联网重算
               |
       核对结果仍对应当前列表
               |
          保存并更新路线
```

地点删除和算路结果是两次独立更新。高德失败不会撤销用户的删除；用户在查询中继续改动时，旧响应不得覆盖新路线。编辑备注或停留时间不改变道路路径，只有影响地点和顺序的修改触发相应重算。

## 路由与静态部署

保留现有静态导出方案，先用固定页面加查询参数：

```text
/?day=2026-10-03
/map?day=2026-10-03
/place?day=2026-10-03&stop=stop-123
/place/edit?day=2026-10-03&stop=stop-123
```

地点 ID 在浏览器中读取，页面入口只包装相应客户端 Screen。避免给用户临时创建的每个地点设计必须在构建时生成的页面路径。Vinext 官方静态导出实现说明，动态 App Router 路由需要 generateStaticParams；这一限制支持使用固定页面加运行时参数的选择。[官方实现](https://github.com/cloudflare/vinext/blob/main/packages/vinext/src/build/static-export.ts)

进入实施后，需用归档锁定的 Vinext 版本验证查询参数页面和客户端水合行为。现有 serve.mjs 目前主要服务根页面，必须补齐新增页面的 HTML / RSC 路径映射；深链接刷新、返回及断网打开都要验证，不能只测首页。

部署结构：

```text
手机 / 电脑
     |
     v
域名 HTTPS（Nginx / Caddy）
     |
     v
Node serve.mjs
 +-- 静态 PWA 页面与资源
 +-- /api/amap-config
 +-- /_AMapService/*  --> 高德服务

每台设备：IndexedDB 保存本机路书和有效路线缓存
```

IndexedDB 适合结构化本机数据与事务读写；localStorage 仅保留轻量偏好和旧数据迁移读取入口。[MDN IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)

Service Worker 管应用页面、脚本、样式及明确下载的自有资源。构建后生成缓存版本和资源清单；按产物类型正确处理 HTML / RSC，不能把 HTML 返回给 RSC 请求。高德配置接口、代理查询和第三方地图瓦片不纳入通用离线缓存。更新清理限定于本应用旧资源缓存，不清理路书数据库。[MDN 缓存说明](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Caching)

data/seed-trip.json 仅在确认没有现有路书时初始化；public/trip-template.json 如继续提供下载，应由该源生成，避免同时手工维护两份。构建产物放 dist/client，由构建生成，不当源码维护。
